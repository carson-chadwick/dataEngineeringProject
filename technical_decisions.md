# Technical Decisions
---
## Decision 1: Python-driven Ingestion with Prefect vs. Snowflake External Tables

**Context:** The project required a way to ingest clickstream data from a REST API into Snowflake on a recurring schedule to monitor web behavior.

**Decision:** I chose a custom Python script orchestrated by **Prefect** that fetches JSON data, converts it to CSV locally, and executes Snowflake `PUT` and `COPY INTO` commands.

**Alternatives considered:**
- **Snowflake External Tables on S3:** Pointing Snowflake directly at an S3 bucket. This was rejected because the data lived behind a secure REST API rather than in a cloud bucket, requiring a custom "fetcher" regardless.
- **Airflow/Astronomer:** A more complex orchestrator. This was rejected because Prefect’s "Code as Code" approach and local development experience provided a more lightweight and flexible framework for this project's scope.

**Trade-offs:**
- **Pros of chosen approach:** Full control over error handling (try/except) and logging; ability to use Pandas for pre-ingestion cleaning; built-in retries via Prefect tasks.
- **Cons of chosen approach:** Requires managing a Python worker/environment; local temporary file management is necessary for Windows compatibility.

**Rationale:** Using Prefect allowed me to treat ingestion as a first-class citizen with detailed logging and retries. Since the API requires a watermark (timestamp) to pull new data, handling that stateful logic in Python was significantly more intuitive than attempting to orchestrate it purely within Snowflake SQL.

## Decision 2: Schema-on-Read (VARCHAR) vs. Schema-on-Write (Numeric) for Foreign Keys

**Context:** During Milestone 1 and 2, the pipeline encountered a `Numeric value not recognized` error (Snowflake Error 100038) when joining email marketing campaigns (containing UUID strings) to sales orders (containing integers).

**Decision:** I standardized all Join Keys (IDs) as **VARCHAR/String** in the staging layer by using explicit casting (`::string`).

**Alternatives considered:**
- **Filtering out UUIDs:** Only processing numeric IDs. This was rejected because it would result in significant data loss and ignore valid real-time events generated by the web API.
- **Snowflake `TRY_CAST`:** Attempting to cast to integer at join time. This was rejected because it makes the join logic brittle and can significantly degrade query performance on large datasets.

**Trade-offs:**
- **Pros:** High pipeline resilience; the warehouse never crashes due to "dirty" or mixed ID formats; simplifies joins between disparate systems like PostgreSQL, MongoDB, and REST APIs.
- **Cons:** Slight storage overhead in Snowflake compared to optimized integers; loss of native numeric validation at the database level.

**Rationale:** In a modern data stack where data originates from multiple sources (NoSQL, SQL, and APIs), expecting perfectly consistent data types is unrealistic. Casting to string at the staging layer follows the "ELT" philosophy: get the data in safely first, then handle the business logic in dbt.

## Decision 3: Modular dbt Architecture (Staging -> Intermediate) vs. Monolithic Models

**Context:** The final requirement was to provide downstream analysts with enriched web analytics data that included customer demographic and geographic information.

**Decision:** I implemented a multi-layered dbt approach using a dedicated **Intermediate Model** (`int_web_analytics_with_customers`) to perform the enrichment join.

**Alternatives considered:**
- **Joining in the BI Layer:** Performing the join inside a tool like Tableau or Evidence. This was rejected because it forces every analyst to write the same join logic, leading to "metric drift" and inconsistent reporting.
- **One Big Staging Model:** Joining customer data directly inside the `stg_web_analytics` model. This was rejected because staging models should strictly reflect their source; adding a join there violates the modularity and lineage standards of dbt.

**Trade-offs:**
- **Pros:** Promotes "DRY" (Don't Repeat Yourself) code; creates a "Wide Table" that is easy for non-technical users to query; keeps staging models clean and 1:1 with source tables.
- **Cons:** Increases the number of models to manage; adds one more "hop" in the data lineage which slightly increases build time.

**Rationale:** The intermediate layer acts as the "translation" layer of the warehouse. By pre-joining the web events to the customer dimension, I ensured that every analyst uses the same definitions for geography and segments, creating a more reliable and governed reporting environment.
